# LoRA Set Builder

A small local web app that turns a few source photos — or only a text description — into a
curated, captioned training set for a character LoRA. Images are generated by
**Qwen-Image-2.1** running in **ComfyUI** (local or on a RunPod pod); the app plans the shots,
queues the generations, lets you compare and pick variants, and exports a dataset plus an
**ai-toolkit** config for training a Qwen-Image-2.1 LoRA.

```
 sources / description ──► references ──► shot list ──► N variants per take ──► pick ──► captions ──► dataset.zip + ai-toolkit.yaml
                               ▲                              │  (regenerate, correct)
                               └── anchor / turnaround sheet ─┘
```

## Install and run

```bash
pip install -r requirements.txt
python run.py projects/anna          # creates the project folder on first run
```

The browser opens at <http://127.0.0.1:7861/>. Each project is a folder with `project.yaml`
(all settings, takes and picks), `sources/`, `takes/<id>/` (generated variants) and `export/`.
You can edit `project.yaml` by hand while the app is stopped.

### ComfyUI side

ComfyUI must be recent enough to have the Qwen-Image-2.1 nodes (`TextEncodeQwenImage21`,
`QwenImage21Cache`). Model files, from `Comfy-Org/Qwen-Image-2.1` on Hugging Face:

| folder | file |
|---|---|
| `models/diffusion_models/` | `qwen_image_2.1_int8_convrot.safetensors` (or `_bf16`) |
| `models/text_encoders/` | `qwen3vl_8b_int8_convrot.safetensors` (or `_bf16`) |
| `models/vae/` | `qwen_image_2.1_vae_bf16.safetensors` |

On RunPod, expose port 8188 and put `https://<pod-id>-8188.proxy.runpod.net` in **Setup → ComfyUI
URL**. **Test connection** checks that the nodes and the three model files are there.

**Password.** RunPod's official ComfyUI template will not start ComfyUI without a
`COMFYUI_PASSWORD` (12+ characters). A small proxy on port 8188 checks it on every request.
Enter the same password in **Setup → ComfyUI password**. The app sends it as
`Authorization: Bearer <password>`, which that proxy accepts from scripts. It is saved in
`.secrets.yaml`, not `project.yaml`, and the `COMFYUI_PASSWORD` environment variable overrides
it. A missing or wrong password shows as a 401 error. After ten wrong attempts in a row the proxy
answers 429 for a while; the app reports both plainly. Leave the field empty for a ComfyUI with no
password, such as a local one.

### RunPod serverless instead of a pod

In **Setup → Where ComfyUI runs**, choose **RunPod serverless endpoint**, then enter the endpoint
ID and your RunPod API key. The key is saved in `.secrets.yaml` in the project folder, not in
`project.yaml`; the `RUNPOD_API_KEY` environment variable overrides it. You pay only while images
are being made, and RunPod can run several workers in parallel, so a full shot list finishes
faster.

The endpoint must run RunPod's official ComfyUI worker
([runpod-workers/worker-comfyui](https://github.com/runpod-workers/worker-comfyui), v5 or later).
The app sends the same workflow as for a pod, with the reference images included in the request.
RunPod caps a request at 10 MB, so references are sent as JPEGs of about 1.2 MP. That is above
the model's own 1024² budget for references, so no detail is lost.

**How the worker gets ComfyUI and the models.** A serverless worker is a Docker image that RunPod
starts when a job arrives and stops when it is idle. Nothing persists between starts, so the
models must either be in the image or on a network volume:

1. **In the image** (simplest; `serverless/Dockerfile`). It starts from the worker's `-base`
   image, moves ComfyUI to a version with the Qwen-Image-2.1 nodes, and downloads the three int8
   model files (~16 GB) into the image. Build it, push it to Docker Hub, and create the endpoint
   from it:
   ```bash
   cd serverless
   docker build --platform linux/amd64 -t <you>/lsb-qwen21-worker:1 .
   docker push <you>/lsb-qwen21-worker:1
   ```
   Pros: no volume, works in any region with any GPU. Cons: a large image. The first start on a
   new machine pulls it, which takes several minutes; after that RunPod caches it.
2. **On a network volume.** Build with `--build-arg BAKE_MODELS=0` and attach a network volume to
   the endpoint. Serverless workers mount it at `/runpod-volume` and read models from
   `/runpod-volume/models/`. The worker's path map uses ComfyUI's older folder names, so:
   ```
   /runpod-volume/models/unet/qwen_image_2.1_int8_convrot.safetensors     (diffusion model)
   /runpod-volume/models/clip/qwen3vl_8b_int8_convrot.safetensors         (text encoder)
   /runpod-volume/models/vae/qwen_image_2.1_vae_bf16.safetensors
   /runpod-volume/models/loras/<your round-1 LoRA>.safetensors
   ```
   The easiest way to fill the volume is a cheap temporary pod with the volume attached; on a pod
   it appears as `/workspace`, so the same files go under `/workspace/models/...`. Pros: a small
   image, and you can add LoRAs without rebuilding. Cons: the endpoint is tied to the volume's
   data centre and the GPUs available there. Loading 16 GB from a volume on a cold start is also
   slower than from local disk.

For round 2 (**LoRA while generating**) the LoRA has to be on the worker too: on the volume under
`models/loras/`, or added to the Dockerfile.

Endpoint settings worth changing: **execution timeout** at least 600 s (a cold start loads all
the models before the first image). **Idle timeout** 60–120 s, so one worker stays warm across a
batch. **Max workers** sets how many takes run in parallel. **Test connection** for serverless
only reaches `/health`. Missing nodes or model files show up as an error on the first variant,
because the worker checks the model files before it runs.

To try the app without a GPU, run the bundled fake server: `python tools/mock_comfy.py` and
use `http://127.0.0.1:8188` (add `--password <pw>` to imitate the template's password proxy). It returns placeholder images but checks that every submitted
graph is wired correctly. It also imitates the RunPod serverless API: start the app with
`RUNPOD_API_BASE=http://127.0.0.1:8188/v2`, choose serverless, and use any endpoint ID and key.

## The workflow

### 1. Setup
Name, trigger word (e.g. `ohwx`), class word (`man`, `woman`, `person`, `character`), and the
subject type:

- **Real person** — identity comes from the photos. Keep the description short.
- **Invented character** — identity comes from the description (include the art style if it is
  not a photo).

### 2. Sources
Drop in whatever photos you have. Tick **Reference** on 2–4 clear, well-lit, unobstructed
ones (a front face and a three-quarter view are the most useful). These are sent to the model
with every take. **In dataset** puts the real photo itself in the training set — real photos are
the best training material you have, so keep them in unless they are poor.

*No photos?* In the shot list, **Add anchor**. It generates the character from the description
alone; pick the best variant and press **Use as reference** in the large view. Then **Add
reference sheet** (a turnaround: front, three-quarter, profile, back), pick the best one and make
it a reference too. From there on every take is built from those references, which keeps the
character consistent.

### 3. Shot list
**Add default set** creates a set of takes (20 by default) that cycle through framing (≈35 % close-up, 40 % medium,
25 % full body), eight camera angles, six expressions, eight outfits, twelve settings and six
lighting setups, without repeating combinations. Tick *keep the same outfit* for a character
whose costume is part of its identity. Every field is editable. Expand a row (▸) to see the exact
prompt, add extra instructions, write a prompt by hand, or override the caption.

Take modes:

| mode | what it sends | use it for |
|---|---|---|
| **from refs** | references as `<image1>…<imageN>`, empty canvas at the take's aspect ratio | most takes |
| **edit photo** | one source photo as `<image1>` (canvas follows it) + other references | keeping the real face pixels, changing clothes/background/lighting |
| **text only** | nothing; prompt from the description | the anchor |

### 4. Generate & pick
**Generate all takes not yet tried** queues *N* variants (default 4) for each take; ComfyUI works
through its queue and results appear as they finish. For each take:

- click an image to see it large next to the references it was made from; **←/→** moves between
  variants, **P** picks;
- one is close? Open it, type what to change (“hair shorter, no glasses”) in **Refine** and
  press Enter. This queues *N* edits of that exact image: it is sent as `<image1>` with
  “change only this, keep everything else”, and the canvas follows it. The first refinement reuses
  the original's seed, so it stays closest to it; the others get new seeds. Refinements carry a
  *refined* badge and can be refined again. They send only that image, without the references or
  the identity lock, so a correction to the face or hair is not overruled. The caption still comes
  from the take, so if a refinement changes something the caption mentions (outfit, setting),
  edit the take to match;
- none close? Type in the box under the take and **Apply and generate**. That text is added to
  the take's prompt and the new variants start from scratch with new seeds. It replaces what was
  in the box before, so repeat earlier corrections you want to keep;
- **Clear unpicked** deletes the rejects;
- **Generate more for takes with no pick** tops up every take that still has no pick.

With `insightface` installed (`pip install insightface onnxruntime`) each variant gets a
face-similarity score against the references, which makes the right one easier to find among
many. It is a sorting aid only, and it is not useful for stylised characters.

### 5. Export
Shows a balance report (framing, angles, takes without a pick, shared captions) and writes:

```
export/dataset/001_source.png + 001_source.txt …     images (long side ≤ 1536) + captions
export/<name>_ai_toolkit.yaml                         training config, arch qwen_image_2
export/<name>_dataset.zip                             both, ready to upload to the pod
```

Captions are `trigger class, framing, angle, expression, outfit, setting, lighting`. They
deliberately say nothing about the face or hair, so the LoRA ties those to the trigger word.

## Round 2: bootstrapping

When the source material is very thin, the first set is often good but not great. Train a
short LoRA on it (≈1000 steps), copy the `.safetensors` file into ComfyUI's `models/loras/`, set
**LoRA while generating** in Setup (strength 0.6–0.9) and generate again. The LoRA and the
references now work together, so likeness and variety both improve. Replace weaker picks, export
and train the final LoRA.

## Other approaches (and when to choose them)

1. **Reference editing (this app).** One open model, no extra tools, works from a single photo.
   Weak spot: unusual angles the references never show (back of the head, strong profile) can
   drift. A reference sheet helps.
2. **Bootstrapped LoRA** (round 2 above). Best when you have 3–6 photos: the v1 LoRA fills in
   angles and expressions the references alone cannot.
3. **Video orbit.** Run an image-to-video model (e.g. Wan or LTX) on one good photo with a
   slow camera orbit or a head turn, and pull sharp frames out of the clip. It gives very
   consistent identity across many angles from a single photo. Lighting and setting stay the same,
   so mix these frames with edited takes rather than using them alone. The app's sources accept
   these frames directly.
4. **Face swap / identity adapters** (ReActor, PuLID, InstantID on a separate base model):
   generate varied bodies and scenes, then put the face in. Fast, but often leaves a slightly
   pasted-on face and skin texture that a LoRA learns too; generally weaker than 1–3 now.
5. **No LoRA at all.** Qwen-Image-2.1 accepts up to ten reference images, so for occasional
   images of one subject the reference workflow on its own may be enough. A LoRA is worth it
   when you need the subject often, with prompts only, or combined with other references.

## Practical notes

- **Set size.** 15–30 varied, picked images is a comfortable size; quality matters more than
  quantity. Reject anything with a wrong face, extra fingers or a garbled background — the LoRA
  learns defects.
- **Use real photos.** Only use photos of people who have agreed to it.
- **Licence.** Qwen-Image-2.1 is released under the Qwen Research License; commercial use needs a
  separate licence from Alibaba. A LoRA trained on it inherits that.

## What was tested

The full flow (sources, default shot list, all three take modes, picking, refining, promoting
anchors to references, export) was run against `tools/mock_comfy.py`, which checks graph wiring but does not
run the model. Not yet run against a real ComfyUI:

- the graph in `lsb/graph.py` follows the official template
  `image_qwen_image_2_1_image_edit.json`, flattened from its subgraph. If ComfyUI rejects it, the
  error on the variant names the node and input; that file is the only place to change;
- the ai-toolkit config adapts ai-toolkit's Qwen-Image example to `arch: qwen_image_2`
  (Qwen-Image-2.1). Compare it with the defaults the ai-toolkit UI offers for Qwen-Image-2.1
  before a long run;
- the insightface scoring;
- the serverless path against a real endpoint, and `serverless/Dockerfile` (it was not
  built). In particular, check that the `COMFYUI_REF` checkout works on top of the worker image.
  If it does not, build the worker repository itself with
  `--build-arg COMFYUI_VERSION=<a version with the Qwen-Image-2.1 nodes>`.
